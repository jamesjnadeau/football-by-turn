# Cut Block Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give offensive linemen a new pre-snap stance — "tucked special" — that on
the first turn of a play throws an instant cut block: the nearest defender ahead
of him is shoved back 2 yards. The turn after, the lineman is slow but grinds
out much more friction over a much wider area, and any teammate standing within
a yard of him runs faster and responds to a new direction quicker.

**Architecture:** The mechanic is a two-phase extension of the existing stance
system (`player.mode`, see `lib/game/modes.js` and `state.js`'s `setMode`): a
new `'cutBlock'` mode for the commit turn (player-selectable, offensive
linemen only, first turn of a play only) that fires a one-shot scripted
displacement exactly like `rules.js`'s fumble pop-out, and a new
`'cutBlockDrive'` mode for the turn after (never player-selectable — `turn.js`
walks a lineman into and out of it automatically, the same way it already
zeroes `charge` every turn). A new module, `lib/game/block.js`, owns
everything specific to the maneuver: the instant push, the extra collision
reach a driving blocker grants everyone who touches him, and the proximity
scan that grants nearby teammates their speed and agility boost.
`modes.js`/`physics.js`/`turn.js` each gain the few lines needed to read that
module's numbers, following the exact pattern already used for `cover.js`
(imported into `physics.js` for `grabBonus`, into `turn.js` for
`updateCoverPlans`).

**Tech Stack:** Plain ES modules, `node --test` (`npm test`). No new
dependencies.

**Spec:** The user's own description, quoted in full because there is no
separate spec document for this feature:

> when an offensive linemen enters their tucked special on the first turn of a
> play, they will perform a cut block. This lunges them forward with a lot of
> force, pushing the defensive player back 2 yards. The offensive player then
> can't move very fast for the next turn, but is able to cause much greater
> friction and by a larger area to the defensive players around them. Any
> offensive player within 1 yard of this player gains a speed boost, but so
> they can cover more ground, and they are also able to turn quicker, this is
> to simulate players using their own team mate to help them move.

This plan argues from that paragraph the way the game's own plan
(`docs/superpowers/plans/2026-08-29-football-by-turn-game.md`) argues from
`README.md`; executors should read both this plan and the paragraph above.

## Global Constraints

- No npm dependencies, no build step, no DOM/`node:` imports inside
  `lib/game/` — the whole codebase's existing rule (see the game plan's own
  Global Constraints), and this feature adds nothing that needs to break it.
- All physics stays in SVG units; 1 yard = 3.75 units. Every new distance
  constant is written as a raw unit literal with the yard conversion spelled
  out in its comment, matching every existing constant in `constants.js`.
- `state.turnIndex === 0` is this codebase's existing, already-used meaning of
  "first turn of a play" (see `turn.js:54`, `play.js:28`, `state.js:172`) —
  reuse it; do not invent a second "is this the first turn" test.
- Constants only ever go in `lib/game/constants.js`. Every number this plan
  introduces is named and justified there, never inlined at its call site.
- Comment style: prose explaining **why**, matching the density and voice of
  the surrounding file. Do not write comments that only restate the code.
- `npm test` (`node --test test/game/`) must pass after every task.

## Design decisions (resolving spec ambiguities — read before implementing)

The paragraph above describes a maneuver, not an implementation. These are
the calls this plan makes; each links to a task where the reasoning lives in
code comments too.

1. **Two internal mode names, one player-facing "tucked special".** The spec
   describes two different turns of behavior (the lunge, then the grind), and
   this codebase's `player.mode` field is exactly the "what kind of turn is
   this player having" state machine already (`tucked`/`prepared`/`holding`).
   Rather than bolt a second field onto the player, this plan adds two modes:
   `'cutBlock'` for the lunge turn (what the coach actually selects — the
   "tucked special" of the spec) and `'cutBlockDrive'` for the grind turn
   (entered automatically, never by the coach). Task 4 is what walks a player
   from one to the other and back to `'normal'`, the same way `turn.js`
   already walks `charge` from 1 back to 0 every turn.
2. **Who, and when.** "Offensive linemen" = the five interior roles every
   roster in `rosters.js` already uses for its line: `C`, `LG`, `RG`, `LT`,
   `RT` (Task 1 names this set `OFFENSIVE_LINE_ROLES`). "The first turn of a
   play" = `state.turnIndex === 0`, this codebase's existing meaning of that
   phrase.
3. **The push is a scripted displacement, not physics.** "Pushing the
   defensive player back 2 yards" is a discrete, one-time event — the
   engine's only existing precedent for that is `rules.js`'s `dropBall` (the
   fumble pop-out), which moves the ball by a fixed offset rather than
   letting collision physics work it out over a turn. Task 2's
   `applyCutBlock` follows the same pattern: it runs once, the instant the
   lineman commits to the stance (inside `setMode`, before the turn's own
   physics ever runs), not once per sub-step.
4. **Which defender gets cut.** The spec says "the defensive player" as if
   there is an obvious one: the man the lineman is squared up on. This plan
   picks the nearest defender within engagement range **inside the same
   forward wedge every other stance already strikes in**
   (`STANCE_CONE_HALF_ANGLE`, the angle `tackleReach`/`inStanceCone` use) —
   so a cut block hits the man lined up in front of him and never one lined
   up behind or beside him. A lineman with nobody in front of him still
   enters the stance; the lunge just finds nothing to hit.
5. **"Much greater friction... by a larger area" is collision reach, not
   mass.** The spec asks for a bigger *area of effect*, not for the blocker
   to become harder to move himself (unlike `holding`, which gets both a
   friction bump AND `HOLD_MASS_MULT`). Task 3 gives `'cutBlockDrive'` a
   higher friction coefficient than `holding`'s and, separately, extends
   *everyone's* collision contact distance against him — not one assigned
   man's, the way `cover.js`'s `grabBonus` works, but anyone who comes near.
   It does **not** touch `effectiveMass`: nothing in the spec asks for the
   blocker himself to become harder to push, and adding that would be a
   mechanic the request didn't call for.
6. **"Within 1 yard" is measured edge-to-edge, not centre-to-centre.** Two
   adjacent players' centres are already 5–7 units apart just from their own
   radii (a lineman's radius alone is 3.5 units) — comfortably more than
   3.75 units (1 yard), so a literal centre-distance reading of "within 1
   yard" could never fire for two players standing next to each other. Every
   existing reach-like constant in this codebase (`PREPARED_REACH`,
   `HOLD_REACH`, `COVER_GRAB_REACH`) is instead "extra distance past the two
   bodies' own radii", and Task 5 measures the assist aura the same way:
   `dist(a, b) - a.radius - b.radius <= CUT_BLOCK_ASSIST_RADIUS_UNITS`.
7. **The assist is speed + acceleration, not agility.** "Turn quicker" is
   read as *accelerates toward a new target velocity faster* —
   `accelMult`, the exact mechanic `charge` already uses for "the burst after
   setting your feet" — rather than as loosening `STANCE_LATERAL_MULT` for a
   stanced player caught in the aura. Most assisted teammates are in
   `'normal'` mode anyway, where there is no lateral/forward distinction to
   loosen; `accelMult` is the one number that means "responds to a new
   direction faster" for every mode uniformly.
8. **Recomputed every sub-step, never latched.** Whether a player is in the
   aura is read fresh before every `stepPhysics` call, the same slot
   `cover.js`'s `updateCoverPlans` already fills — so the boost tracks the
   block as both men move through the turn, instead of freezing whoever
   happened to be close at the instant the drive phase began.
9. **Not fixed by this plan:** `predict.js` replays a single player's own
   `steer()` on a throwaway clone to preview his destination circle, and
   already ignores collisions, cover, and every other cross-player effect —
   it will likewise not reflect a `cutBlockAssist` boost picked up mid-preview.
   This is the same pre-existing simplification the destination preview
   already lives with for every other multi-player effect in the game, not a
   gap this feature opens; fixing it is out of scope.

// --- cut block ("tucked special": a lineman's cut block) ---
// An offensive lineman (OFFENSIVE_LINE_ROLES, rosters.js) may commit to this
// stance only on the first turn of a play (state.turnIndex === 0) — a cut
// block is called at the line, not drawn up mid-down. Committing arms the
// same CHARGE_MULT burst every stance grants (setMode, above) and fires a
// discrete shove the instant he commits (applyCutBlock, block.js) — unlike
// an ordinary block, the push is not something physics has to resolve over
// the turn.
export const CUT_BLOCK_ENGAGE_UNITS = 4;       // ~1.1 yd of engagement range
// past the two bodies' own radii: how far away a defender may stand dead
// ahead of the blocker and still be the one who gets cut. Wide enough to
// reach the man lined up across from him, not the next gap over.
export const CUT_BLOCK_PUSH_UNITS = 7.5;       // spec: 2 yards, × 3.75 units/yard
export const CUT_BLOCK_IMPULSE_SPEED = 30;     // u/s the cut defender carries
// out of the shove, so he visibly staggers away rather than teleporting inert
// — below a skill player's own top speed (60 u/s), a stagger and not a
// launch. Ordinary IDLE_DAMPING bleeds it off same as any riderless velocity.
export const CUT_BLOCK_DRIVE_SPEED_MULT = 0.3; // spec: can't move very fast
// the turn after — between HOLD_SPEED_MULT (0.15, "severely limited") and
// TUCK_SPEED_MULT (0.85, "a little slower"): driving hard, not going far.
export const CUT_BLOCK_DRIVE_REACH = 6;        // ~1.6 yd of EXTRA contact
// distance for anyone who touches a driving blocker (physics.js's
// driveReachBonus) — double HOLD_REACH (3): the spec's "much greater
// friction ... by a larger area".
export const FRICTION_CUT_BLOCK_DRIVE = 0.75;  // above FRICTION_HOLD (0.6):
// "much greater friction" than an ordinary held block.
export const CUT_BLOCK_ASSIST_RADIUS_UNITS = 3.75; // spec: within 1 yard,
// measured edge-to-edge (see the plan's design decision 6) — × 3.75 units/yard.
export const CUT_BLOCK_ASSIST_SPEED_MULT = 1.25;   // spec: a speed boost
export const CUT_BLOCK_ASSIST_ACCEL_MULT = 1.5;    // spec: turns quicker — the
// same weight as CHARGE_MULT: "responds to a new direction faster" is exactly
// what accelMult means everywhere else in this file.

- [ ] **Step 4: Create `lib/game/block.js`**

```js
/**
 * The cut block: an offensive lineman's "tucked special". Committing to it
 * on the first turn of a play (setMode, state.js) fires a discrete shove
 * against the nearest defender ahead of him — the one thing in this game
 * that moves a player by a scripted offset rather than letting physics work
 * it out over a turn, the same trick dropBall (rules.js) uses for a fumble's
 * pop-out. The turn after, turn.js walks him from this stance into the drive
 * phase (cutBlockDrive), where he is slow but hard to slide past —
 * modes.js and physics.js are where that phase's numbers actually live;
 * this file only owns the instant that starts it and the aura around it.
 */
import { add, sub, len, norm, scale, dot } from './vec.js';
import { CUT_BLOCK_ENGAGE_UNITS, CUT_BLOCK_PUSH_UNITS, CUT_BLOCK_IMPULSE_SPEED, STANCE_CONE_HALF_ANGLE } from './constants.js';

const CONE_COS = Math.cos(STANCE_CONE_HALF_ANGLE);

/**
 * The nearest defender ahead of `blocker` within cutting range, or null.
 * "Ahead" is the same wedge every other stance strikes in
 * (STANCE_CONE_HALF_ANGLE) measured against `heading` — the axis setMode is
 * about to freeze into `facing` — so a cut block only ever hits the man he
 * is squared up on, never someone lined up behind or beside him.
 */
function cutTarget(state, blocker, heading) {
  let best = null;
  let bestDist = Infinity;
  for (const d of state.players) {
    if (d.team !== 'defense') continue;
    const toD = sub(d.pos, blocker.pos);
    const dd = len(toD);
    if (dd === 0 || dd > blocker.radius + d.radius + CUT_BLOCK_ENGAGE_UNITS) continue;
    if (dot(norm(toD), heading) < CONE_COS) continue;
    if (dd < bestDist) { best = d; bestDist = dd; }
  }
  return best;
}

/**
 * The lunge: pushes the nearest defender ahead of `blocker` straight back
 * CUT_BLOCK_PUSH_UNITS and sets him staggering away at
 * CUT_BLOCK_IMPULSE_SPEED. Called once, from setMode, at the instant the
 * lineman commits — not a per-sub-step effect, so it happens before the
 * turn's own physics ever runs. Whatever the shove leaves overlapping a
 * third player is untangled by the very next stepPhysics call the same way
 * any other overlap is; this function does not resolve collisions itself.
 *
 * Returns the defender who was cut, or null if nobody was in range — a whiff
 * is legal; the lineman still enters the stance (setMode already decided
 * that), he just has nobody in front of him to cut.
 */
export function applyCutBlock(state, blocker, heading) {
  const target = cutTarget(state, blocker, heading);
  if (!target) return null;
  const dir = norm(sub(target.pos, blocker.pos));
  target.pos = add(target.pos, scale(dir, CUT_BLOCK_PUSH_UNITS));
  target.vel = scale(dir, CUT_BLOCK_IMPULSE_SPEED);
  return target;
}
```

/**

export function advanceCutBlockPhases(state) {
